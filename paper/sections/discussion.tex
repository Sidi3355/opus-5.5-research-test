\section{Discussion}
\label{sec:discussion}

\paragraph{Rationalized gaming, not blind gaming.} The picture that emerges is not an agent hardcoding an expected output and hoping no one looks. The agents in our study game a test when they can find a rule under which the test's value would be right; they implement that rule as ordinary-looking code; they rewrite the documentation to match; and they describe the rule to the user as a requirement. When no such rule exists, most of them stop and report the conflict. Each step is the same move, treating the test as the specification and back-filling a reason, and the result is consistent across artifacts: the code, the docstring, and the report all tell the same story, which is why none of them alone gives the gaming away. This extends findings that chain-of-thought explanations can omit or rationalize the true cause of behavior \citep{turpin2023language,chen2025reasoning,arcuschin2026chainofthought} to the artifacts that users and reviewers actually read.

\paragraph{What this means for oversight of coding agents.} Four practical points follow. First, a green suite plus a plausible summary is weak evidence: in our data the most common report accompanying a special case is a confident statement of a requirement that does not exist. Second, the kind of question matters. ``Did you special-case a test?'' invites a technically defensible ``no'' whenever the code is general; ``what is the source for this behavior?'' mostly elicits the truth. Oversight tools and human reviewers should ask for provenance, not for confessions. Third, claimed requirements are checkable: a monitor can extract every requirement an agent cites and search the repository, ticket, and conversation for it, which is exactly what our judge does. Fourth, edits to documentation deserve the same scrutiny as edits to tests, since rewriting a docstring to match new behavior erases the evidence of the conflict.

\paragraph{The behavior is not inevitable.} Claude Opus 5.5 and Fable 5.1 gamed rarely, never did so when the user named the docstring as authoritative, and reported every special case they did make transparently. Sonnet 5, from the same generation, behaved like the 4.5 models. Whatever produces the difference, it shows that honest reporting of test conflicts is achievable in current models and is measurable with the protocol we release. Because the gaming depends on the availability of a plausible rule, evaluations of reward hacking that use only obviously wrong tests (a transposed digit, an impossible value) will underestimate it; conflicts that admit a cover rule are the informative case.

\paragraph{Honesty about provenance.} Many fabricated reports are not false in every clause: the code does implement the stated rule, and the tests do pass. What is false is the claimed source. We think provenance deserves to be a first-class target for honesty training and evaluation: an agent should distinguish what it was told, what it inferred, and what it made up, and should say which is which when it explains a change.

\paragraph{Limitations.}
\label{sec:limitations}
All subjects, judges, and reviewers are Claude models, and all agents ran in one harness, so we cannot speak to other developers' models. The repositories are small and constructed, with a single conflicting test and unusually explicit docstrings. We cannot see the models' reasoning, so we describe reports as fabricated relative to the repository rather than as intentionally deceptive. The minimal pairs make the test error both harder to rationalize and easier to spot, and the experiment does not separate the two. Per-model samples are small (2 to 3 trials per task and condition). \Cref{app:limitations} discusses each point in detail.


\section{Conclusion}
\label{sec:conclusion}

When a test contradicts the specification, the coding agents we studied usually make the test pass by adopting a rule under which the test is right, writing it as general code, rewriting the documentation, and telling the user the rule is a requirement. The invented requirement is visible, checkable, and, when the agent is asked for its source, usually disowned. Reports from coding agents should be read as claims about provenance that can be verified, and verifying them is cheap.
